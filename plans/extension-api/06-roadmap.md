## Approach to the rebuild

The new code replaces the old code in the same package folders (`02#Target workspace`). The owner decided
where that happens: approach A (`00#Owner decisions` 11). The table records the approaches that were considered.

| Approach                                    | Shape                                                                                                                                                                                             | Verification                                                                                                      | Risks and mitigation                                                                                                                                                                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A (decided).** Long-lived branch          | An integration branch, `codex/extension-api-rebuild`, starts from `main`. Its first change deletes the old sources. Each work package is a pull request into it. One merge into `main` at release | CI runs on each pull request into the branch. At release, `main` gets one merge, and `pnpm run prepublish` passes | The branch drifts from `main`. Mitigation: `main` takes only 0.6.x fixes and tooling updates, and the branch merges `main` after each one. The last merge is large. Mitigation: it was reviewed as work packages, and CI was green     |
| B. New packages beside the old, then switch | New workspaces (`packages/core-next`, ...) on `main`. Old and new build together. A last change deletes the old folders and renames the new ones                                                  | Both sets pass `pnpm run build` and `pnpm run test` until the switch. The switch passes `pnpm run check:all`      | Two workspaces cannot share the name `@oxform/core`, so temporary names, aliases and `exports` are written twice. The switch is a second migration. `explorations/` keeps importing old source. Mitigation: none that removes the cost |
| C. Rebuild on `main`, 0.6.x on a branch     | `main` loses the old sources at once. A `release/0.6` branch holds 0.6.x                                                                                                                          | CI on `main`                                                                                                      | `main` cannot be published or deployed for the whole rebuild. If the docs site deploys from `main`, the public site breaks (`04#10`). Mitigation: move the deploy source, which is a change outside this plan                          |

Decided: A. It is the only approach where nothing is written twice (KISS), no temporary name exists
(YAGNI), and the old sources are deleted first (delete aggressively). `04#10` already assumes "the rebuild
branch". Rejected: a compatibility layer between old and new (direction, "Goal").

Rules for approach A:

- **`main` and 0.6.x.** `main` stays on 0.6.x and stays publishable. A 0.6.x fix is made on `main` and is not
  ported: the new code is written new. The public docs site serves 0.6 until the release (`04#10`).
- **Branches and commits.** A work package branch is `codex/<work-package-id>-<short-name>`. Commits are
  conventional commits with lowercase subjects, one purpose each (`AGENTS.md`, "Git & GitHub").
- **A green branch.** The integration branch must pass its exit criteria at the end of each phase. A check that
  has no content yet (for example example tests) is absent, not skipped.
- **`explorations/`.** It stays as a reading reference until phase 9. It stops building when P1-01 lands
  (`02#Target workspace`). P0-03 tags the last commit where it builds. P9-02 deletes the folder.
- **`plans/`.** It stays until the roadmap is complete (`02#Target workspace`). P9-05 removes this folder.
- **Side effects.** A tag, a branch, a version bump, a merge into `main` and a publish each need the owner's
  approval (`AGENTS.md`, "Autonomy").

   old pages do not compile after the old packages are deleted.

   package branch is `codex/<work-package-id>-<short-name>`, as `AGENTS.md` asks for the `codex/` prefix.
